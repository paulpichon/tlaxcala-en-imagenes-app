### 📊 Project Health Status

El frontend de TlaxApp está construido con un stack moderno (Next.js 16 + React 19 + TypeScript 6 + Bootstrap 5.3) y muestra una arquitectura bien pensada con separación de responsabilidades, uso correcto de Server/Client Components, y manejo de estado mediante Context API. Sin embargo, existe **un bloqueador crítico de producción**: todas las llamadas a la API apuntan exclusivamente a `localhost:5000` (`NEXT_PUBLIC_API_URL_LOCAL`), ignorando la variable de entorno `NEXT_PUBLIC_API_URL` diseñada para producción. Adicionalmente, el `Service Worker` para notificaciones push nunca se registra, y el `FavoritoProvider` se duplica en múltiples layouts anidados, causando reseteo de estado. La documentación técnica (`docs/technical-analysis.md`) ya identifica varios de estos problemas.

### 🔴 Crítico

#### 1. URL de API hardcodeada a entorno local — rotura total en producción

* **Issue:** Cada llamada a la API (autenticación, posteos, notificaciones, follow, favoritos) usa `process.env.NEXT_PUBLIC_API_URL_LOCAL` (→ `http://localhost:5000`). En producción, el navegador intentará conectarse a `localhost:5000`, lo que **provocará que todas las peticiones fallen**.
* **Location:** Múltiples archivos, entre ellos:
  - `src/context/AuthContext.tsx:28` → `const API_URL = process.env.NEXT_PUBLIC_API_URL_LOCAL;`
  - `src/context/NotificacionesContext.tsx:34` → `` `${process.env.NEXT_PUBLIC_API_URL_LOCAL}/api/notificaciones/nuevas-notificaciones` ``
  - `src/context/FollowContext.tsx:29` → `` `${process.env.NEXT_PUBLIC_API_URL_LOCAL}/api/followers/...` ``
  - `src/context/NuevosUsuariosContext.tsx:48` → `` `${process.env.NEXT_PUBLIC_API_URL_LOCAL}/api/usuarios/...` ``
  - `src/context/FavoritoContext.tsx:41` → `` `${process.env.NEXT_PUBLIC_API_URL_LOCAL}/api/favoritos/...` ``
  - `src/lib/actions.ts:42,59,132,209,219` → todas usan `NEXT_PUBLIC_API_URL_LOCAL`
  - `src/app/hooks/useInfinitePosts.ts:24` → `` `${process.env.NEXT_PUBLIC_API_URL_LOCAL}${nextUrl}` ``
  - `src/app/hooks/usePushNotifications.ts:76,90` → `` `${process.env.NEXT_PUBLIC_API_URL_LOCAL}/api/notificaciones/...` ``
* **Documentación de referencia:** `AGENTS.md` (GOTCHA #2: "API URL not environment-aware in actions.ts"), `README.md` (menciona ambas variables `NEXT_PUBLIC_API_URL` y `NEXT_PUBLIC_API_URL_LOCAL`)
* **Impact:** **La aplicación entera queda inoperativa en producción.** Ninguna llamada API funcionará. Esto incluye login, registro, feed, posteos, comentarios, likes, follows, favoritos, notificaciones, y perfil.
* **Código evidencia:**
  ```typescript
  // AuthContext.tsx:28
  const API_URL = process.env.NEXT_PUBLIC_API_URL_LOCAL;

  // NotificacionesContext.tsx:34
  `${process.env.NEXT_PUBLIC_API_URL_LOCAL}/api/notificaciones/nuevas-notificaciones`
  ```

#### 2. `actions.ts` usa `fetch` directo sin `fetchWithAuth` para flujos que requieren autenticación

* **Issue:** Las funciones `reenviarCorreo()`, `reenviarCorreoRestablecerPassword()`, y `envioCorreoRestablecerPassword()` en `src/lib/actions.ts` usan `fetch` nativo con `credentials: 'include'`, pero **no implementan el patrón de refresh automático** que provee `fetchWithAuth`. Si el token JWT ha expirado, estas peticiones fallarán sin posibilidad de renovación automática.
* **Location:** `src/lib/actions.ts:49-214` — funciones `reenviarCorreo`, `reenviarCorreoRestablecerPassword`, `envioCorreoRestablecerPassword`
* **Documentación de referencia:** `AGENTS.md` (sección Auth Pattern describe `fetchWithAuth`)
* **Impact:** Los flujos de reenvío de correo y restablecimiento de contraseña pueden fallar silenciosamente si el token de sesión expiró, llevando a una experiencia de usuario confusa.
* **Código evidencia:**
  ```typescript
  // actions.ts:56-59
  funcionRequestOptions( raw );
  const response = await fetch(`${process.env.NEXT_PUBLIC_API_URL_LOCAL}/api/auth/reenviar-correo`, requestOptions);
  ```

### 🟠 Alto

#### 1. `FavoritoProvider` duplicado en 4 layouts anidados — estado volátil entre rutas

* **Issue:** El `FavoritoProvider` se declaga en 4 layouts anidados distintos (`inicio/layout.tsx`, `configuracion/layout.tsx`, `notificaciones/layout.tsx`, `posteo/[idposteo]/layout.tsx`), en lugar de una sola instancia en el layout raíz. Cada provider crea su propio estado en memoria (`favoritosMap`, `loadingMap`). Si el usuario navega de `/inicio` a `/configuracion`, el estado de favoritos se resetea porque se monta un nuevo provider.
* **Location:**
  - `src/app/inicio/layout.tsx:16-19`
  - `src/app/configuracion/layout.tsx:30-33`
  - `src/app/notificaciones/layout.tsx:27-30`
  - `src/app/posteo/[idposteo]/layout.tsx:39-42`
* **Documentación de referencia:** `DOCUMENTACION.md`, `docs/technical-analysis.md`
* **Impact:** Datos inconsistentes de favoritos entre rutas. El estado optimista de toggleFavorito puede perderse al cambiar de página, causando que el UI muestre un estado distinto al real.
* **Evidencia adicional:** El `FavoritoContext` ni siquiera se importa en el `root layout` (`src/app/layout.tsx`), lo que significa que cualquier componente fuera de los layouts anidados que intente usar `useFavorito()` lanzará un error en runtime.

#### 2. Service Worker para notificaciones push nunca se registra

* **Issue:** El archivo `public/sw.js` existe y contiene la lógica para recibir y mostrar notificaciones push. El hook `src/app/hooks/usePushNotifications.ts` implementa la funcionalidad completa de registro (solicitar permiso, obtener clave VAPID, suscribirse, notificar al backend). Sin embargo, **ningún componente o layout invoca `usePushNotifications()`**, por lo que el Service Worker jamás se registra y las notificaciones push nunca funcionan.
* **Location:**
  - `public/sw.js` — Service Worker listo pero no registrado
  - `src/app/hooks/usePushNotifications.ts` — Hook completo pero no invocado
* **Documentación de referencia:** `AGENTS.md` ("Push notifications: `public/sw.js` (Service Worker)")
* **Impact:** Las notificaciones push están completamente inoperativas. Los usuarios nunca recibirán alertas de nuevos seguidores, likes o comentarios.
* **Recomendación:** Invocar `usePushNotifications()` desde un componente que se monte al autenticarse, típicamente en el feed (`/inicio`) o en el layout principal.

#### 3. Estado mutable global en `actions.ts` — riesgo de condición de carrera

* **Issue:** La variable `requestOptions` se declara como variable de módulo (`let requestOptions: RequestInit;` fuera de cualquier función) y la función `funcionRequestOptions(raw)` la muta. Si dos llamadas a funciones en `actions.ts` ocurren concurrentemente (ej. `createUsuario` y `reenviarCorreo`), pueden pisar los headers/configuración de la otra.
* **Location:** `src/lib/actions.ts:15-24`
* **Impact:** Las requests podrían enviarse con un `body` incorrecto o headers desactualizados, causando errores 400/500 intermitentes difíciles de depurar.
* **Código evidencia:**
  ```typescript
  let requestOptions: RequestInit;  // Variable global del módulo
  function funcionRequestOptions(raw: BodyInit) {
      requestOptions = {  // Mutación
          method: "POST",
          credentials: 'include',
          headers: myHeaders,
          body: raw,
          redirect: "follow",
      };
  }
  ```

### 🟡 Medio

#### 1. Sin scripts de lint, type-check, ni tests en `package.json`

* **Issue:** El `package.json` solo define `dev`, `build`, y `start`. No hay `lint`, `typecheck`, ni scripts de prueba. Cualquier error de TypeScript solo se detecta en build. No hay ESLint configurado.
* **Location:** `package.json:5-9`
* **Impact:** El código puede contener errores de tipo que pasan desapercibidos durante el desarrollo. La ausencia de pruebas aumenta el riesgo de regresiones.
* **Documentación de referencia:** `AGENTS.md` (GOTCHA #1: "No lint/typecheck scripts")

#### 2. Import duplicado de Bootstrap CSS

* **Issue:** `bootstrap/dist/css/bootstrap.css` se importa en el root layout (`src/app/layout.tsx:4`) y nuevamente en `src/components/ProtectedRoute.tsx:9`. Esta duplicación no causa errores pero incrementa innecesariamente el bundle.
* **Location:**
  - `src/app/layout.tsx:4` → `import 'bootstrap/dist/css/bootstrap.min.css';`
  - `src/components/ProtectedRoute.tsx:9` → `import "bootstrap/dist/css/bootstrap.css";`
* **Impact:** Mínimo, pero indica falta de limpieza. Además, nótese que uno importa `bootstrap.min.css` y el otro `bootstrap.css` (versiones distintas).

#### 3. Comentarios en idioma mixto (español/inglés)

* **Issue:** Aunque la mayoría del código está documentado en español, algunos archivos mezclan comentarios en español e inglés, y variables/modules como `requestOptions`, `myHeaders`, `funcionRequestOptions` combinan estilos de nomenclatura en inglés con nombres de función en español.
* **Location:** Principalmente `src/lib/actions.ts`, parcialmente en otros archivos.
* **Impact:** Bajo desde el punto de vista funcional, pero perjudica la consistencia del proyecto y la legibilidad para futuros mantenedores.

#### 4. Hooks de página mezclados con hooks compartidos

* **Issue:** Los hooks personalizados residen en `src/app/hooks/`, lo que los vincula conceptualmente a las páginas. Sin embargo, hooks como `useInfinitePosts`, `useCrearPosteo`, o `useComentarios` son funcionalidad compartida y podrían estar en `src/hooks/` a nivel raíz.
* **Location:** `src/app/hooks/` (11 archivos)
* **Impact:** Bajo desde el punto de vista funcional, pero la estructura sugiere que estos hooks solo se usan desde páginas. En la práctica, hooks como `useComentarios` podrían ser útiles desde componentes.

### 🟢 Bajo

#### 1. `userScalable: false` bloquea zoom en móviles — accesibilidad reducida

* **Issue:** El viewport global declara `userScalable: false` y `maximumScale: 1`, lo que impide que los usuarios hagan zoom en dispositivos móviles. Esto viola las pautas de accesibilidad WCAG (pauta 1.4.4: "Resize Text").
* **Location:** `src/app/layout.tsx:69-74`
* **Impact:** Usuarios con discapacidad visual no pueden ampliar el contenido. Puede ser problemático para cumplimiento de accesibilidad.
* **Código evidencia:**
  ```typescript
  export const viewport: Viewport = {
    width: 'device-width',
    initialScale: 1,
    maximumScale: 1,
    userScalable: false,
  };
  ```

#### 2. Documentación excesiva inline en componentes

* **Issue:** Varios componentes (especialmente `favoritos/page.tsx`, `notificaciones/page.tsx`, `configuracion/page.tsx`) contienen comentarios extremadamente detallados que documentan comportamiento obvio (ej. "Contenedor del contenido principal - Publicaciones favoritas"). Esto infla el tamaño de los archivos sin aportar valor real.
* **Location:** `src/app/favoritos/page.tsx`, `src/app/notificaciones/page.tsx`, `src/app/configuracion/page.tsx`
* **Impact:** Mínimo. Los comentarios excesivos pueden volverse ruido y desactualizarse, pero no afectan la funcionalidad.

### 🔧 Recommended Action Plan

#### Inmediatas (Riesgo de producción — resolver antes del próximo deploy)

1. **Desacoplar la URL de API del entorno:**
   - Crear `src/lib/api.ts` con una función centralizada:
     ```typescript
     const API_BASE_URL = process.env.NEXT_PUBLIC_API_URL || process.env.NEXT_PUBLIC_API_URL_LOCAL || 'http://localhost:5000';
     export function apiUrl(path: string): string {
       const normalized = path.startsWith('/') ? path : `/${path}`;
       return `${API_BASE_URL}${normalized}`;
     }
     ```
   - Reemplazar **todas** las ocurrencias de `process.env.NEXT_PUBLIC_API_URL_LOCAL` con `apiUrl(...)`.

### Resumen de Fortalezas Identificadas

A pesar de los hallazgos críticos, el proyecto tiene bases sólidas:

1. **Arquitectura de Context API bien segmentada** — 6 contextos con responsabilidades claras
2. **Patrón de refresh token con concurrencia** (`isRefreshing` + `refreshPromise`) — robusto contra race conditions
3. **Uso correcto de Server Components** para páginas y Client Components solo para interactividad
4. **Scroll infinito** implementado con IntersectionObserver (buena performance)
5. **Validación con Zod 4** — cobertura completa de schemas (registro, posteo, comentarios, spam)
6. **Seguridad**: JWT cookie-based (HttpOnly), sin tokens en localStorage, `credentials: 'include'` en todas las peticiones
7. **Cloudinary presets seguros** que evitan `f_auto`/`q_auto`/`g_auto` para prevenir el bug de imágenes rotas
8. **SEO consciente**: `robots.ts` bien configurado, páginas privadas con `noindex`, JSON-LD para datos estructurados
9. **Documentación técnica existente** (`docs/technical-analysis.md`, `AGENTS.md`) que ya identifica varios problemas — hay conciencia del equipo sobre la deuda técnica
10. **Manejo de errores HTTP** con códigos de estado específicos (429, 401, 403, 500) y mensajes contextuales

### Observaciones Finales

El proyecto TlaxApp está bien estructurado conceptualmente, con una clara separación entre capas (contextos, hooks, componentes, páginas) y uso de tecnologías modernas del ecosistema Next.js. Sin embargo, el **bloqueador crítico de la URL de API hardcodeada a localhost** representa un riesgo inmediato para cualquier deploy a producción. Se recomienda priorizar la corrección de este punto antes que cualquier otra tarea, seguida de la consolidación de `FavoritoProvider` en el root layout y la activación del Service Worker para notificaciones push.

La puntuación de 42/100 refleja que, si bien la deuda técnica es significativa, las correcciones son localizadas y no requieren reestructuraciones profundas. Con un sprint enfocado en los items "Inmediatas" y "Corto plazo", la puntuación podría subir a ~70/100.

*Alcance no confirmado en su totalidad para el hallazgo de `userScalable: false` en dispositivos específicos; se recomienda prueba manual en iOS Safari y Chrome Android para verificar el comportamiento.*
