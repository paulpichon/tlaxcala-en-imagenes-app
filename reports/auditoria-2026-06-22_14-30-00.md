### 📊 Project Health Status

El frontend consume **37 endpoints únicos**, todos documentados en `API.md`. Sin embargo, se detectaron **11 discrepancias críticas de nomenclatura de campos** entre lo que el frontend espera y lo que `API.md` documenta, lo que provocaría fallos en tiempo de ejecución en funcionalidades cardinales (likes, favoritos, seguidores, notificaciones push, feed). La documentación (`DOCUMENTACION.md` y `AGENTS.md`) contiene afirmaciones incorrectas sobre el hardcoding de `API_URL_LOCAL`. 7 endpoints documentados en `API.md` no son consumidos por el frontend (algunos esperados, como health-check y bienvenida). **0 endpoints** son llamados por el frontend sin estar documentados.

---

### 🚨 Critical Inconsistencies

* **❌ 11 discrepancias de nombres de campos entre API.md y el código frontend.**  
  Esto representa el mayor riesgo: 8 de ellas romperían funcionalidades por completo, 3 degradarían la experiencia. Se detallan en la tabla de hallazgos.

* **❌ Documentación contradictoria sobre API_URL.**  
  `DOCUMENTACION.md` (sección 22) y `AGENTS.md` afirman que `actions.ts` usa `NEXT_PUBLIC_API_URL_LOCAL` hardcodeado, pero el código real usa `process.env.NEXT_PUBLIC_API_URL` correctamente.

### 🔧 Recommended Action Plan

#### Prioridad 1: Corregir discrepancias críticas de campos (Hallazgos 1-8)

Estos 8 hallazgos causan fallos funcionales totales. Se recomienda **alinear el frontend con API.md** (o viceversa si la API ya se actualizó y la documentación no). La solución más segura es estandarizar contra API.md:

1. **`useLikes.ts:67-69`** — Cambiar `"Like añadido"` → `"Like agregado exitosamente"` y `"Like eliminado"` → `"Like eliminado exitosamente"`
2. **`FavoritoContext.tsx:64`** — Cambiar `"Agregado en Favoritos"` → `"Agregado a favoritos"`
3. **`types.ts:183-185`**, `useLikes.ts:34`, `useLikesModal.ts:29` — Cambiar `likes_usuarios_posteo` → `usuarios`
4. **`FollowersModal.tsx:38`** — Cambiar `data.seguidores` → `data.followers`
5. **`FollowingModal.tsx:35`** — Cambiar `data.siguiendo` → `data.followings`
6. **`usePushNotifications.ts:80`** — Cambiar `const { key }` → `const { publicKey: key }` (desestructuración con alias)
7. **`useObtenerUbicacion.ts:51-54`** — Cambiar `{ lat: ..., lng: ... }` → `{ latitude: coords.latitude, longitude: coords.longitude }`
8. **`types.ts:83`** y `useInfinitePosts.ts:31` — Cambiar `posteosConEstado` → `posteos` (o viceversa si el backend usa `posteosConEstado`)

#### Prioridad 2: Corregir hallazgos altos (Hallazgos 9-12)

9. **`NotificacionesContext.tsx:40`** — Cambiar `data.totalNoLeidas` → `data.nuevasNotificaciones`
10. **`NuevosUsuariosContext.tsx:55`** — Cambiar `data.nuevosUsuariosRegistrados` → `data.usuarios`
11. **`useObtenerUbicacion.ts:62-64`** — Cambiar `data.municipio` → `data.lugar_radicacion`
12. **`useNotifications.tsx:22`** — Cambiar `?page=${pagina}&limit=15` → `?desde=${(pagina-1)*limite}&limite=20` o negociar con backend los nombres de parámetros

#### Prioridad 3: Sincronizar documentación (Hallazgos 15)

- Actualizar `DOCUMENTACION.md` sección 22 para reflejar que `actions.ts` usa `NEXT_PUBLIC_API_URL` (no `LOCAL`).
- Actualizar `AGENTS.md` para corregir la misma afirmación.

#### Prioridad 4: Investigar y alinear (Hallazgos 13, 14, 16, 17, 20)

- Verificar si el backend acepta los campos extra en `POST /api/favoritos/:posteoId` y `PUT /api/posteos/:id`
- Confirmar si el endpoint `POST /api/ayuda-soporte/envio-correo` fue rediseñado para aceptar `tipo_problema`/`descripcion_problema_usuario` en lugar de los campos documentados
- Decidir si los endpoints sin autenticación deben usar `fetchWithAuth` o `fetch` directo
