# Documentación del Proyecto: Tlaxcala en Imágenes App (TlaxApp)

## 1. Resumen General

**TlaxApp** es una red social enfocada en el estado de Tlaxcala, México. Permite a los usuarios compartir fotografías, descubrir lugares, conectar con personas de la comunidad y vivir Tlaxcala a través de imágenes. La aplicación está orientada a personas residentes o interesadas en la cultura, turismo y vida cotidiana de Tlaxcala.

**Características principales:**
- Registro y autenticación con verificación de correo electrónico
- Publicación de fotografías con texto opcional y geolocalización por municipio
- Feed de publicaciones públicas de otros usuarios con scroll infinito
- Sistema de likes, comentarios, seguidores y favoritos
- Perfil de usuario con grid de publicaciones
- Notificaciones push vía Web Push (VAPID)
- Gestión de cuenta (editar perfil, eliminar cuenta, ayuda y soporte)
- Publicidad rotativa en barra lateral
- Interfaz completamente en español (es_MX)

**Usuarios objetivo:** Residentes y visitantes del estado de Tlaxcala que deseen compartir y descubrir contenido visual de la región.

### 7.2 Patrón Arquitectónico

El proyecto sigue un **patrón híbrido** que combina:

1. **Arquitectura basada en features (App Router):** Las rutas están organizadas por funcionalidad (`/inicio`, `/cuentas`, `/configuracion`, `/favoritos`, `/notificaciones`, `/posteo`). Cada ruta tiene su propio layout, página y componentes locales.

2. **Separación por capas:** Existe una clara separación entre:
   - **Capa de presentación:** Componentes en `src/app/components/`
   - **Capa de estado:** Contextos en `src/context/`
   - **Capa de servicios:** Cliente API en `src/lib/apiClient.ts` y acciones en `src/lib/actions.ts`
   - **Capa de tipos:** Interfaces centralizadas en `src/types/types.ts`
   - **Capa de validación:** Esquemas Zod en `src/lib/validaciones.ts`

**Evidencia del código:**
- Los layouts anidados (`layout.tsx` en cada subdirectorio) encapsulan providers específicos (ej: `FavoritoProvider` en `/inicio` y `/perfil`)
- Los hooks personalizados (`src/app/hooks/`) encapsulan la lógica de negocio y las llamadas a la API
- Los contextos globales (`src/context/`) se inyectan en el layout raíz
- Los componentes de protección (`ProtectedRoute`, `AlreadyAuthRedirect`) están en `src/components/` como wrappers reutilizables

### Mecanismo de Protección

La protección de rutas se implementa mediante el componente `ProtectedRoute` (`src/components/ProtectedRoute.tsx`), que:
1. Verifica el estado `user` y `loading` del `AuthContext`
2. Si `loading` es `true` o no hay usuario, muestra un `Spinner`
3. Si no hay usuario y terminó la carga, redirige a `/cuentas/login`
4. Si hay usuario autenticado, renderiza los children

El componente inverso, `AlreadyAuthRedirect` (`src/components/AlreadyAuthRedirect.tsx`), redirige a `/inicio` si el usuario ya está autenticado (usado en la landing page y páginas de autenticación).

## 9. Gestión de Estado

El proyecto utiliza **React Context API** como mecanismo principal de gestión de estado global. No se usa Redux, Zustand, MobX ni ninguna otra biblioteca de estado externo.

### 9.1 AuthContext (`src/context/AuthContext.tsx`)

**Propósito:** Gestionar la sesión del usuario, incluyendo login, logout, refresco de token y actualización de datos.

**Estado:**
```typescript
{
  user: UsuarioLogueado | null;  // Datos del usuario autenticado
  loading: boolean;               // Indicador de carga inicial
}
```

**Acciones expuestas:**
| Acción | Descripción |
|--------|-------------|
| `login(user)` | Establece el usuario en memoria y limpia sessionStorage/localStorage temporal |
| `logout()` | Llama a `POST /api/auth/logout`, limpia el estado y las cookies |
| `updateUser(newData)` | Actualiza parcialmente los datos del usuario en memoria |
| `fetchWithAuth(input, init)` | Wrapper de `fetch` con refresco automático de token en caso de 401 |

**Refresco de token:**
- Al inicializar, hace `GET /api/auth/me` para obtener el usuario actual
- Si recibe 401, intenta `POST /api/auth/refresh` automáticamente
- Usa `useRef` para evitar múltiples refreshes simultáneos (patrón de deduplicación con promesa compartida)
- `fetchWithAuth` reintenta hasta 2 veces con backoff exponencial en errores de red

**Hook:** `useAuth()` — debe usarse dentro de `AuthProvider`

### 9.2 NotificacionesContext (`src/context/NotificacionesContext.tsx`)

### 9.4 NuevosUsuariosContext (`src/context/NuevosUsuariosContext.tsx`)

## 10. Capa de API

### 10.1 Cliente HTTP Centralizado (`src/lib/apiClient.ts`)

Todas las llamadas a la API backend se realizan a través de funciones centralizadas que:
1. Construyen la URL completa usando `NEXT_PUBLIC_API_URL`
2. Incluyen `credentials: 'include'` para enviar cookies httpOnly
3. Detectan automáticamente `FormData` vs JSON
4. Procesan la respuesta con `handleApiResponse` que lanza `ApiError` en caso de error

**Funciones disponibles:**

| Función | Método HTTP | Descripción |
|---------|-------------|-------------|
| `apiGet<T>(fetchFn, path, params?, init?)` | GET | Consulta con query params opcionales |
| `apiPost<T>(fetchFn, path, body?, init?)` | POST | Envío de datos (JSON o FormData) |
| `apiPut<T>(fetchFn, path, body?, init?)` | PUT | Actualización de recursos |
| `apiPatch<T>(fetchFn, path, body?, init?)` | PATCH | Actualización parcial |
| `apiDelete<T>(fetchFn, path, init?)` | DELETE | Eliminación de recursos |

**Parámetro `fetchFn`:** Las funciones aceptan un `FetchFunction` que puede ser `fetch` nativo (para endpoints públicos) o `fetchWithAuth` del `AuthContext` (para endpoints autenticados con refresco automático de token).

### 10.2 Manejo de Errores

**Clase `ApiError`:**
```typescript
class ApiError extends Error {
  status: number;        // Código HTTP
  data: ApiErrorData;    // Cuerpo del error RFC 9457
}
```

**Helpers de detección de errores:**

| Función | Descripción |
|---------|-------------|
| `isApiError(err)` | Verifica si el error es una instancia de `ApiError` |
| `getApiErrorCode(err)` | Obtiene el código de error (`UNAUTHORIZED`, `NOT_FOUND`, etc.) |
| `isNotFound(err)` | Verifica si es error 404 (`NOT_FOUND`) |
| `isUnauthorized(err)` | Verifica si es error 401 (`UNAUTHORIZED`) |
| `isForbidden(err)` | Verifica si es error 403 (`FORBIDDEN`) |
| `isAuthError(err)` | Verifica si es 401 o 403 |
| `isValidationFailed(err)` | Verifica si es error 422 (`VALIDATION_FAILED`) |
| `isRateLimit(err)` | Verifica si es rate limit (`RATE_LIMIT_EXCEEDED` o cualquier `*_BLOCKED`) |
| `getApiErrorMessage(err, fallback)` | Extrae el mensaje legible del error |
| `getUserMessage(err, operacion)` | Genera un mensaje amigable para el usuario según la operación |
| `getValidationErrors(err)` | Extrae errores de validación por campo |

**Códigos de error (`ApiErrorCode`):**
```
BAD_REQUEST, UNAUTHORIZED, FORBIDDEN, NOT_FOUND, CONFLICT,
VALIDATION_FAILED, RATE_LIMIT_EXCEEDED, INTERNAL_ERROR,
LOGIN_BLOCKED, RECOVERY_BLOCKED, EMAIL_BLOCKED, REGISTER_BLOCKED,
POSTEO_BLOCKED, SOPORTE_BLOCKED, READ_BLOCKED, COMENTARIO_BLOCKED,
REFRESH_BLOCKED, FILE_ERROR, INVALID_JSON
```

**Mensajes por operación (`getUserMessage`):** El sistema tiene mensajes predefinidos para 20+ operaciones (comentar, crear_posteo, like, follow, etc.) que se usan como fallback cuando el error de la API no tiene un `detail` legible.

**Retorno:** `{ lat, lng, obtenerUbicacion, loadingUbicacion, ubicacionError, municipioId, ciudad, estado, pais, setters }`

### 12.9 usePushNotifications
**Ubicación:** `src/app/hooks/usePushNotifications.ts`
**Descripción:** Gestiona la suscripción a notificaciones push del navegador usando Web Push (VAPID). Registra un Service Worker (`/sw.js`), solicita permiso, obtiene la clave pública VAPID del backend y envía la suscripción.

**Retorno:** `{ estado, activarNotificaciones, desactivarNotificaciones }`

**Estados posibles:** `"idle"`, `"pending"`, `"enabled"`, `"disabled"`, `"error"`

### 12.10 useUsuarioPerfil
**Ubicación:** `src/app/hooks/useUsuarioPerfil.ts`
**Descripción:** Carga el perfil público de un usuario por su URL/slug desde `GET /api/usuarios/:url`.

**Retorno:** `{ usuario, loading, error, isNotFoundError, clearError, setUsuario }`

**Manejo especial:** Trata `VALIDATION_FAILED` (URL mal formada) como equivalente a `NOT_FOUND` para mostrar la página 404.

### 12.11 useLogout
**Ubicación:** `src/app/hooks/auth/logout.ts`
**Descripción:** Hook simple que combina `logout()` del `AuthContext` con redirección a `/cuentas/login`.

**Retorno:** `{ handleLogout }`

## 17. Consideraciones de Seguridad

### Autenticación

- **Almacenamiento de tokens:** Cookies httpOnly (`accessToken` y `refreshToken`). No se almacenan tokens en `localStorage` ni `sessionStorage`.
- **Refresco automático:** El `AuthContext` detecta respuestas 401 y renueva el token automáticamente vía `POST /api/auth/refresh`.
- **CSRF:** El backend valida el header `Origin`/`Referer` en métodos mutantes. El frontend envía `credentials: 'include'` en todas las llamadas.
- **Cookies:** `httpOnly: true`, `secure: true`, `sameSite: 'none'`, `path: '/'`.

### Tokens Temporales

- **sessionStorage:** Se usa para almacenar tokens temporales de verificación de correo (`registroToken`) y restablecimiento de contraseña (`passForgetToken`). Estos se limpian al hacer login.
- **localStorage:** Se usa para `lastPasswordRequest` y `bloqueoReenvioCorreo` (control de cooldown). También se limpian al hacer login.

### Datos Sensibles

- No se encontraron API keys, secretos ni credenciales hardcodeadas en el código fuente del frontend.
- Las variables `NEXT_PUBLIC_*` son de frontend y no contienen información sensible.
- La imagen de publicidad en `PublicidadContext.tsx` contiene URLs de Cloudinary con enlaces a negocios locales (no es información sensible).

### XSS

- No se detectó uso de `dangerouslySetInnerHTML` con contenido dinámico del usuario. El único uso es para JSON-LD (datos estructurados estáticos).
- Los textos de publicaciones y comentarios se renderizan como texto plano dentro de elementos JSX.

### Protección de Rutas

- Las rutas privadas están protegidas con `ProtectedRoute` a nivel de layout.
- Las páginas públicas de autenticación usan `AlreadyAuthRedirect` para evitar que usuarios autenticados las vean.
- El SEO de páginas privadas está configurado con `robots: { index: false, follow: false }`.

### Robots.txt

El archivo `robots.ts` bloquea el acceso de crawlers a:
- `/api/`
- `/posteo/`
- `/configuracion/`
- `/notificaciones/`

## 23. Problemas Conocidos y Limitaciones

1. **Sin infraestructura de testing:** El proyecto no tiene ningún tipo de prueba automatizada (unitarias, integración, E2E).

2. **Sin linting ni formateo:** No hay herramientas de calidad de código configuradas.

3. **Publicidad hardcodeada:** Los anuncios publicitarios están definidos como constantes en `PublicidadContext.tsx` con URLs específicas de Cloudinary y enlaces a negocios locales. No hay un sistema de gestión de anuncios.

4. **`fetchWithAuth` vs `fetch`:** Las funciones de `actions.ts` usan `fetch` nativo (para endpoints públicos de autenticación), mientras que los hooks y contextos usan `fetchWithAuth` del `AuthContext`. Esta dualidad es correcta pero requiere atención al agregar nuevas llamadas.

5. **`date-fns` sin uso:** La dependencia `date-fns` está instalada pero no se encontraron usos en el código. Las fechas se formatean con `Intl.DateTimeFormat`.

6. **Directorio `api/early-access/` vacío:** Existe una ruta API sin implementar.

7. **FavoritoProvider no es global:** El `FavoritoContext` se inyecta solo en layouts anidados (`/inicio` y `/(perfil)/[url]`), no en el layout raíz. Esto significa que fuera de esas rutas, el contexto no está disponible.

8. **No hay reports previos:** El directorio `reports/documentador/` está vacío, por lo que no hay documentación previa para comparar cambios estructurales.
